# Security and Safety Notes

**Commit this document describes:** see `FOUNDATION_IMPLEMENTATION_REPORT.md` for the exact SHA.

Plain statement of the actual security and safety posture after this foundation pass — what's real, what's deliberately scoped out, and why. Not a claim of completeness.

## Authentication

- JWT access tokens (`app/security/tokens.py`), 15-minute expiry, HS256, signed with a `JWT_SECRET` that fails closed at boot if missing (`app/config.py` — `Settings` has no default for it).
- Refresh tokens: opaque random values (`secrets.token_urlsafe(48)`), stored server-side only as SHA-256 hashes, never the raw value. Rotation is transactional (Phase 2): consuming the old token and inserting its successor happen in one explicit Postgres transaction, so a mid-rotation failure rolls back to a coherent, retryable state instead of stranding the user. Replay of an already-consumed token revokes the entire token family, verified with a real forced `UniqueViolationError`, not a mock.
- Account state (`is_active`, `deleted_at`) is checked against Postgres directly on **every** authenticated request (`get_current_user`), not just a Redis TTL artifact — a disabled/deleted account's existing access tokens stop working immediately, verified with a real test that disables an account mid-session and reuses its still-unexpired token.
- Redis unreachability fails closed (`503`), never silently treated as "not revoked" (`401`) — this distinction is deliberately preserved and tested.

## Consent

- `consent_events` is append-only: granting always inserts a new row. The one narrow, deliberate exception is `withdrawn_at`, set on the currently-active row by a withdrawal — never a rewrite of what was actually granted historically.
- `/analyze` requires a valid, current-policy-version consent grant (`REQUIRED_CONSENT_TYPE`/`REQUIRED_POLICY_VERSION` in `app/db/consent_repository.py`) before any CV work happens. An old policy version or a withdrawn grant both correctly deny analysis.

## Safety enforcement (allergies, avoid-ingredients, pregnancy/nursing, sensitive skin)

- `SafetyEngine`/`SafetyDecision` (`app/domain/safety_engine.py`) replaces the old inline, undocumented pregnancy/nursing exclusion. Every priority and product-category candidate gets a real, machine-readable decision recorded in `plan.metadata.safety_decisions`.
- **`PlanService.generate_plan()` still produces the abstract, category-level plan** via `app/domain/product_safety.py`'s `CATEGORY_SAFETY_PROFILES` (`evaluate_offer()`) — unchanged. **What is no longer true**: that this abstract plan is the end of the line. `app.domain.recommendation_service.apply_product_matching_and_routine_safety()` now runs on top of it (the real production path, both for `/analyze` and the async worker, via the shared `compute_analysis()`), resolving each category to concrete catalog products through `ProductMatchingService` + `SafetyEngine.evaluate_product_formulation()` — this is the actual P0 closure: **every concrete product recommendation this application ever returns has passed formulation-level safety evaluation**, never produced from `evaluate_offer()`'s category-level check alone. See `PRODUCT_RECOMMENDATION_PIPELINE.md`.
- `SafetyEngine.evaluate_product_formulation(pool, formulation_id, constraints)` evaluates real ingredient data from a normalized catalog (`PRODUCT_CATALOG_ARCHITECTURE.md`) — real allergy/avoid-ingredient conflicts (resolved through ingredient-alias matching, not substring matching), real per-ingredient pregnancy/nursing/sensitive-skin rules, and real pairwise ingredient interactions. An unknown or incomplete formulation returns `INSUFFICIENT_DATA` (`allowed=False`), never `SAFE` — missing ingredient data is never treated as "no unsafe ingredients found." Structurally cannot be influenced by brand/price/commercial ranking: the function's only inputs are a `formulation_id` and the user's own constraints — proven with a real test (`tests/planning/test_formulation_safety.py::test_commercial_factors_cannot_change_safety_result`), not just asserted by the signature.
- **Routine-level safety (`SafetyEngine.evaluate_routine_safety()`) is fail-closed by construction, not just by convention.** `apply_product_matching_and_routine_safety()`'s conflict-resolution pass used to be able to exit with `routine_decision.status == UNSAFE` (an EXCLUDE-action `MAX_FREQUENCY_EXCEEDED`/`BARRIER_RECOVERY_CONFLICT`, or an unresolved `EXCLUDE_COMBINATION` its pairwise heuristic couldn't attribute to a droppable step) while still attaching every step's concrete product recommendation regardless — a real P0 bug, fixed this pass. The invariant now enforced, with a hard backstop for the cases the heuristic itself can't resolve: **`routine_decision.status == UNSAFE` can never coexist with a non-empty `product_recommendations`.** When the routine can't be made safe, every step's concrete candidates are cleared (its abstract category guidance stays untouched) and `plan.metadata.unresolved_unsafe_routine`/`safety_notice` record why, explicitly — never a silent all-empty routine with no explanation. Verified with 5 new tests in `tests/domain/test_recommendation_service.py` covering each unsafe cause independently and the invariant generically.
- The catalog itself (`brands`/`products`/`product_formulations`/`product_skus`/`ingredients`/`ingredient_aliases`/`formulation_ingredients`/`ingredient_rules`/`ingredient_interactions`) is global reference data with `SELECT`-only grants to `skincare_app` — the runtime API role cannot write to any of it (verified with a real `InsufficientPrivilegeError`, `tests/database/test_product_usage_rls.py`). No HTTP route can currently write catalog data at all; population is migration/fixture-only.
- Sensitive skin caps active-ingredient frequency (`SENSITIVE_SKIN_INTENSITY_LIMIT`, currently a hardcoded cap of 2x/week for retinoid-family/acid categories) rather than only appending a disclaimer sentence — the generated routine text itself reflects the real cap, and the disclaimer only claims an adjustment happened when one actually did.
- A beginner's advanced-default concern is no longer dropped outright — it stays visible with a capped `effective_intensity` instead (Phase 15).

## Rate limiting and usage quota (product/usage foundation pass)

- Every real route is now behind an atomic Redis rate limiter (`app/middleware/rate_limiter.py`, single Lua script — `INCR` + conditional `EXPIRE` + threshold check in one round trip, not a racy `GET`-then-`INCR`) — proven under a real concurrent burst to never allow more than the configured limit through (`tests/middleware/test_rate_limiter.py::test_concurrent_requests_at_exact_limit_no_overrun`). `X-Forwarded-For` is honored only from a configured, trusted proxy peer — otherwise a client could forge it to evade IP-based limiting entirely (untrusted-peer case verified directly). Redis-unreachable behavior is per-policy: auth/analysis endpoints fail closed (`503`, never let an unverifiable request through), general authenticated reads fail open (verified both directions against a real unreachable Redis target). Full detail in `USAGE_AND_RATE_LIMIT_ARCHITECTURE.md`.
- `/analyze` now also enforces a per-user, per-period analysis quota (`analysis_usage`, migration `ee276e90a60f`) independent of any billing provider — `app/domain/entitlement.py`'s `EntitlementService`/`UsagePolicyService`, with `FreeTierEntitlementService` (a fixed monthly allowance) as the real default every environment uses today. Reservation is atomic under real concurrent load (`pg_advisory_xact_lock` keyed by user+period, proven to cap concurrent reservations at exactly the configured allowance, not more) and idempotent by `request_id` (a retried request never reserves or consumes quota twice, proven with a real concurrent race producing exactly one reservation from ten identical concurrent calls). A legitimate analysis failure (bad image, no face detected, capture quality too low) releases the reservation rather than consuming it; only a fully successful analysis consumes it. `analysis_usage` has row-level security (`app.current_user_id`-scoped, same pattern as `user_profiles`/`consent_events`), verified with real cross-user isolation tests. Full detail in `USAGE_AND_RATE_LIMIT_ARCHITECTURE.md`.

## Database isolation (P0-1, migration `feb038fd05bd` — complete for all four tables)

- The application's runtime connection (`DATABASE_URL`) uses a restricted `skincare_app` Postgres role — confirmed via direct `pg_roles` query: `rolsuper=false, rolcreatedb=false, rolcreaterole=false, rolbypassrls=false`. It owns no tables; migrations still run as the `postgres` superuser/owner (`alembic.ini`'s `sqlalchemy.url` is unchanged).
- Row-level security is now enabled on **all four application tables**: `user_profiles`, `consent_events` (migration `7b38b717546e`), and `users`/`refresh_tokens` (migration `feb038fd05bd`, this pass). `user_profiles`/`consent_events` use the plain `user_id = current_setting('app.current_user_id')` pattern, `SET LOCAL`-scoped (`set_config(..., true)`) as the first statement of every transaction that touches them.
- `users` and `refresh_tokens` each needed a genuinely different mechanism, not a forced extension of that same pattern, because both have a real pre-authentication access path where no session identity exists yet:
  - `users`: post-auth access (self-lookup by `get_current_user`, self soft-delete in `DELETE /me`) uses the same `id = current_setting('app.current_user_id')` policy. Self-registration (`POST /signup`) has its own `WITH CHECK (true)` INSERT policy — a fresh, app-generated id can't leak any other row. The pre-auth `/login` lookup by email is carved out into `login_lookup_by_email`, a narrow `SECURITY DEFINER` SQL function (owned by the migration's superuser, so it transparently bypasses RLS the way any table-owner query does, without granting `skincare_app` itself a bypass) returning only `id, password_hash` for one exact email. Email is caller-supplied, not a secret, so it deliberately isn't usable as an RLS session-context key the way `user_id` is — that would be no restriction at all. A direct `SELECT ... WHERE email = $1` against the table is now provably blocked pre-auth (tested).
  - `refresh_tokens`: the `user_id`-scoped policy covers every case where identity is already known (successor-token insert, family-wide revocation, `/logout-all`, account-deletion cleanup). A second, OR'd policy scopes by a `app.current_token_hash` session GUC for the genuinely pre-identity token-hash lookups in `/refresh` and `/logout` — a refresh token's hash is a 48-byte random bearer secret, so proof of possession of it (the caller presenting the raw token) is itself a valid access boundary, unlike email. Tested to confirm holding one token's hash exposes only that exact row, not the rest of its family — family-wide revocation still requires the user_id branch, set once the owning user is known from the hash lookup.
- One real bug surfaced and was fixed while building this: Postgres applies a table's SELECT-applicable RLS policy to `INSERT ... RETURNING` as well as `WITH CHECK` — an insert can satisfy `WITH CHECK` and still fail on `RETURNING` if the new row doesn't also pass the SELECT policy. `/signup`'s `id` is now generated in Python (not left to `gen_random_uuid()`'s default) so `app.current_user_id` can be set to it *before* the insert, in the same transaction.
- Cross-user isolation was verified with 14 real PostgreSQL integration tests run through the restricted role (not the superuser, not mocked; `tests/database/test_rls_isolation.py`): User A cannot read/update/delete User B's rows on any of the four tables, even when explicitly querying by User B's ID; a reused pooled connection does not leak context between transactions; the login-lookup function correctly bypasses RLS for exactly one email while the raw table stays closed pre-auth.
- The unauthenticated `/db-check` debug route (`SELECT COUNT(*) FROM users`, no auth, no test coverage) was removed rather than left to silently return 0 once `users` gained RLS — it never set any session identity, so under the new policy it would have queried as nobody.

## Capture quality and CV confidence (Phases 7-11)

- Real head pose (`app/cv/head_pose.py`, `cv2.solvePnP`) and a structured `CaptureAssessment` (`app/cv/capture_assessment.py`, PASS/BORDERLINE/FAIL) now gate `/analyze`: a `FAIL` capture blocks metric computation entirely before any CV math runs on it, rather than silently producing a plan from a bad photo.
- Every one of the 8 skin/face metrics is returned as a `MetricResult` with its own `confidence` and `status` (`app/cv/metric_result.py`, `app/cv/metric_confidence.py`) — an `ABSTAINED` metric (`value=None`) is provably excluded from triggering a personalized concern in `FacialScorer` (`app/ml/scorer.py`), verified with a real test proving this holds regardless of what the withheld underlying value implied.
- **This is not clinical validation.** `calibration_version` is literally `"uncalibrated-1.0"` on every result; see `CV_VALIDATION_LIMITATIONS.md` for the full, honest breakdown of what's measured, what corrupts it, and what remains unsolved (the texture/blur circular dependency, most notably).

## Async analysis submission/execution safety

Full detail in `ASYNC_ANALYSIS_ARCHITECTURE.md` and `RAW_IMAGE_LIFECYCLE.md`. Summary of the safety-relevant properties:

- **Quota ownership is explicit and never doubled.** `AnalysisSubmissionService` reserves the slot exactly once, at submission; `AnalysisExecutionService` never calls `reserve_analysis()` — it only consumes (atomically, inside `commit_analysis_result()`, on success) or releases (`mark_terminal_failure()`, on a terminal outcome only, never on a retryable one). A worker retrying a retryable failure keeps the same reservation; two concurrent workers can never charge a user twice for one logical analysis.
- **The submission failure saga is compensated, not merely attempted once.** `create_request()` failing after a reservation succeeded releases that reservation rather than stranding it `RESERVED` forever. A successful image upload followed by a failed atomic enqueue transaction triggers compensation: attempt deletion of the just-uploaded object; if that itself fails, the DB-side image reference is written independently of the failed transaction so the cleanup sweeper can still recover it later — never silently forgotten.
- **Concurrent first-time submissions of the same `request_id` resolve to one logical analysis**, enforced by real database uniqueness (`analysis_usage.request_id`, `analysis_requests.request_id`, `jobs(job_type, request_id)`), not a process-local lock — a losing concurrent caller polls for the winner's durable row rather than surfacing a bare in-progress error.
- **Strict base64 validation** (`validate=True`) on both the synchronous and async image-decode paths — a payload with characters outside the base64 alphabet fails closed with a domain-level `InvalidImageError`, never silently decoded from whatever valid characters happen to remain.
- **Worker retry classification is a closed, explicit set.** A known-bad-input exception (`NoFaceDetectedError`, `CaptureQualityFailedError`, an invalid image, an invalid/nonexistent durable request state) is always terminal — retrying a bad photo cannot fix it. Everything else defaults retryable, bounded by the job's own `max_attempts`, so an unanticipated failure mode still dead-letters eventually rather than retrying forever.
- **A dead-lettered job always releases quota and marks the durable request `FAILED`** (`AnalysisExecutionService.mark_terminal_failure()`) — the client-facing `GET /api/v2/analyses/{id}` never returns a raw exception message or stack trace for a `FAILED` analysis, only one of a closed set of safe error-code classifications.

## Billing (RevenueCat) — this pass, hardened by independent review (migration `9815eb266923`)

Full detail in `BILLING_ARCHITECTURE.md`. Safety-relevant properties, all tested (`backend/tests/security/test_revenuecat_webhook_verification.py`, `backend/tests/api/test_revenuecat_webhook_route.py`, `backend/tests/database/test_revenuecat_rls.py`, `backend/tests/database/test_revenuecat_billing_privilege.py`):

- **Webhook verification is real, not cosmetic.** HMAC-SHA256 is computed over the exact raw request body bytes (never a parsed-and-reserialized copy — proven by a test that a semantically-identical but differently-whitespaced body fails verification), compared with `hmac.compare_digest` (constant-time), with a bounded timestamp-tolerance window. Neither the Authorization header value, the signing secret, nor the raw HMAC signature is ever logged.
- **No unrestricted write path to premium access — and this claim is now genuinely tested at the role-grant level, not just RLS.** No HTTP route accepts a client-supplied entitlement status. An earlier version of this document made this claim resting only on RLS + a nullable FK, which independent review found insufficient: RLS blocks a write targeting *another* user's row, but did nothing to stop the *ordinary* runtime role (`skincare_app` — what every HTTP request connects as) from writing an `ACTIVE` row for **itself**, since `source_event_id` is nullable specifically to support reconciliation's own corrections. Fixed: `skincare_app` now has **no INSERT/UPDATE/DELETE grant at all** on `user_entitlements` or `revenuecat_webhook_events` — only `SELECT` on `user_entitlements` (what the read path needs). A dedicated, least-privilege `skincare_billing` role (still `NOSUPERUSER`/`NOBYPASSRLS`, still subject to the table's own RLS policy) is the only role that can write either table, and only webhook ingestion, the RevenueCat worker, and reconciliation connect as it. See `BILLING_ARCHITECTURE.md`'s "Database privilege boundary" section for the full grant matrix and both test files that prove it, at two distinct levels: `test_revenuecat_billing_privilege.py` (the ordinary role cannot manufacture billing truth *at all*, self-targeted or not) and `test_revenuecat_rls.py` (RLS itself, exercised through the privileged role). No `DELETE` grant on `user_entitlements` for either role.
- **Never trusts an unvalidated identity string.** A lifecycle event's `app_user_id` must resolve to a real `users.id` or the event fails closed (`FAILED`, `UNKNOWN_APP_USER_ID`) — no entitlement row is fabricated for an unresolvable id. `TRANSFER`'s `transferred_from`/`transferred_to` entries go through the same resolution, but an unresolvable one is skipped rather than a hard failure (see below) — never fabricated into a user either way.
- **`TRANSFER`'s real field contract is now correctly modeled.** An earlier version of this pass incorrectly required `app_user_id` on every event including `TRANSFER`, which does not carry one at all (RevenueCat's real payload carries `transferred_from`/`transferred_to`, always, and `environment`, sometimes). Fixed: required-field validation is event-type-aware; `TRANSFER` requires non-empty `transferred_from`/`transferred_to`, never `app_user_id`. Resolution requires exactly one distinct resolvable local `transferred_to` destination — zero, or more than one distinct one (`AMBIGUOUS_TRANSFER_DESTINATION`), both fail closed to `RECONCILIATION_REQUIRED` rather than granting access to an unintended or multiple unrelated local users. A `TRANSFER` with no resolvable `environment` also fails closed to `RECONCILIATION_REQUIRED` rather than fabricating a SANDBOX/PRODUCTION guess.
- **An unrelated RevenueCat product cannot grant or revoke this app's premium.** An earlier version of this pass applied every supported lifecycle event unconditionally to the configured entitlement, ignoring the event's own `entitlement_ids`. Fixed: every lifecycle mutation now requires `settings.revenuecat_entitlement_id` to appear in the event's `entitlement_ids` (never `null`) before touching `user_entitlements` — a mismatch is a successful, non-retried `NOT_RELEVANT` outcome, not silently ignored and not treated as an error.
- **A refund does not fabricate a renewal-preference change.** An earlier version of this pass set `will_renew=false` on every `cancel_reason=CUSTOMER_SUPPORT` refund, even though refund and auto-renew-off are independent, separately-surfaced facts. Fixed: a refund preserves whatever `will_renew` was already locally projected; only access itself (`status`) is revoked immediately.
- **Out-of-order delivery cannot corrupt state.** A stale event (older `event_timestamp_ms` than what's already projected) is a genuine no-op at the database level (single `INSERT ... ON CONFLICT ... WHERE` statement), not a race-prone read-then-write.
- **A provider outage cannot take down analysis.** `RevenueCatEntitlementService` performs exactly one local `SELECT` through the ordinary runtime pool, proven by a test that fails loudly if it ever constructs an HTTP client.
- **Sandbox purchases cannot grant production access.** `environment` is part of `user_entitlements`' own uniqueness scope, and `RevenueCatEntitlementService` filters by the running environment on top of that.
- **Production fail-closed.** `REVENUECAT_BILLING_ENABLED=true` with any of the four required webhook/API secrets blank/placeholder, or with `REVENUECAT_BILLING_DATABASE_URL` unset/identical to `DATABASE_URL`/carrying a dev marker, refuses to start — same posture as every other production config check in `app/config.py`.

## Catalog ingestion/administration — this pass, hardened by independent review (migrations `37c88143a9ed`, `2de8380d3618`, `13c1fff1867e`, `e5277cf2f0ee`, `154080b29153`; hotfix `fix/catalog-review-identity-binding`, no schema change)

Full detail in `CATALOG_INGESTION_ARCHITECTURE.md`. Safety-relevant properties, all tested (`backend/tests/domain/test_catalog_publication_service.py`, `backend/tests/database/test_catalog_admin_privilege.py`, `backend/tests/database/test_catalog_evidence_immutability.py`, `backend/tests/domain/test_product_matching_publication_gate.py`):

- **Publication is not safety.** `product_formulations.publication_status = 'PUBLISHED'` means "trusted enough for `SafetyEngine` to evaluate," never "safe for every user." Nothing in this pass writes, or could write, a user-specific safety verdict — `SafetyEngine.evaluate_product_formulation()` is unmodified and remains the only source of that determination.
- **A non-published formulation cannot reach a recommendation.** `app/db/catalog_repository.py::list_current_active_formulations_by_category` — the only query `ProductMatchingService` uses for discovery — requires `publication_status = 'PUBLISHED' AND ingredient_data_status = 'COMPLETE' AND is_current = true` simultaneously. `DRAFT`/`NEEDS_REVIEW`/`VERIFIED`/`REJECTED`/`SUPERSEDED` formulations, and `PUBLISHED` ones with incomplete ingredient data, are structurally invisible to that query — proven for every one of those states individually, not just asserted.
- **No unrestricted write path to catalog truth.** `skincare_app` (every HTTP request) has no write grant on any catalog table, staging or production — same architecture, applied from day one, as the corrected billing-role design (`BILLING_ARCHITECTURE.md`). A dedicated `skincare_catalog_admin` role — `NOLOGIN` from creation, no hardcoded password ever, connectable only via a separately-provisioned runtime login — is the only role that can write any of it, and it has no grant whatsoever on `ingredient_rules`/`ingredient_interactions` (rule authoring is out of scope this pass) or on any users/billing/analysis table.
- **Raw evidence immutability, audit append-only-ness, and provenance permanence are database-enforced, not application convention.** An independent review caught that the first version's `skincare_catalog_admin` grants were table-wide, meaning nothing but code review actually stopped that credential from rewriting `raw_payload`, backdating `catalog_audit_log`, or editing `catalog_formulation_provenance`. Fixed (migration `e5277cf2f0ee`): `catalog_import_records` now has column-level `UPDATE` covering only its legitimately-mutable staging fields (`raw_payload`/`payload_sha256`/`external_record_id`/`batch_id`/`created_at` have none), and `catalog_audit_log`/`catalog_formulation_provenance` have no `UPDATE` grant at all. Proven through the real restricted role, not a grant-inspection unit test.
- **No fuzzy matching in any automatic path.** Ingredient and brand/product identity resolution are both exact-match only (the same pre-existing `resolve_ingredient`, reused unmodified). An unresolvable ingredient name becomes a durable, audited human-review item, never an automatic best-guess; a conflicting alias mapping fails closed rather than silently overwriting an existing one.
- **A record cannot become `VALIDATED` by review-item bookkeeping alone.** An independent review caught that resolving *one* of several independent unresolved ingredients on a record could zero out the open-review-item count and incorrectly validate a record still carrying an unresolved ingredient (the publication-time structural backstop still caught it before anything published, but the review state machine itself was wrong). Fixed: `catalog_review_items.identity_key` (migration `154080b29153`) gives each distinct unresolved ingredient its own row, and one canonical function (`app/domain/catalog_validation.py::reconcile_review_state`) — never two independently-maintained copies of the rules — decides `VALIDATED` vs `NEEDS_REVIEW` by re-checking the actual current data, both on the initial pass and after every review resolution.
- **Publication is atomic; reformulation cannot produce two current formulations; concurrent publication of the same record is idempotent.** `CatalogPublicationService.publish()` runs in one transaction, locks the import record (`SELECT ... FOR UPDATE`) before any status decision (an independent review caught that an earlier, unlocked read let two concurrent calls for the same record both walk the create-formulation path), and supersedes the old formulation (`is_current -> false`) strictly before the new one is ever marked current — the database's own pre-existing partial unique index (`idx_product_formulations_one_current_per_market`) makes any other ordering fail outright, not just discouraged by convention. Proven under real concurrent publication attempts (both same-record and same-newly-introduced-brand/product races), not merely read from the code.
- **Untrusted source data cannot exhaust resources, corrupt the catalog, or take down a whole import batch.** Every catalog-admin SQL statement is parameterized; whole-file (50MB), per-record (2MB), per-batch record-count (5000), and per-record ingredient/SKU-count (200/50) bounds are enforced before anything reaches the database — an oversized record's actual content is never persisted, even as evidence. A syntactically valid but non-object JSON value at record position (a bare string/number/boolean/null/array — an independent review found this could raise an unhandled exception and roll back an entire otherwise-valid batch) is classified `MALFORMED`/`NON_OBJECT_RECORD` and persisted as bounded evidence instead, never aborting sibling records.
- **A superseded or rejected formulation, and every raw import record, is retained forever.** No `DELETE` grant exists anywhere for `skincare_catalog_admin`; historical analyses may reference a formulation that is no longer current.
- **Resolving a review item cannot be pointed at the wrong ingredient identity.** An independent review caught that `CatalogReviewService.map_ingredient()`/`create_ingredient()` accepted a caller-supplied `raw_name` and trusted it outright — an operator (or a scripting mistake) could resolve review item A's row while actually creating an alias/ingredient for an unrelated string B, silently marking A `RESOLVED` with its real problem never fixed and never re-surfaced by revalidation. Fixed: `raw_name` is no longer a parameter of either method at all; both derive the raw string exclusively from the review item's own `identity_key`, cross-referenced against the import record's current `normalized_payload` (`CatalogReviewService._resolve_target_raw_name`), and refuse to act if that target no longer resolves to genuinely-unresolved data. Generic `dismiss()` (`MANUAL_OVERRIDE` included) can no longer close an `UNKNOWN_INGREDIENT` item at all — only `map_ingredient()`, `create_ingredient()`, or `reject_import_record()` may.

## Mobile app (`mobile/`) — Mobile V1, Phase A + Phase B + Phase C1

Full detail in `MOBILE_ARCHITECTURE.md`. Safety-relevant properties, all tested (`mobile/tests/`):

- **Bearer/refresh credentials live only in `expo-secure-store`, as a single versioned token-pair value.** Never `AsyncStorage`, SQLite, a plain file, or a persisted TanStack Query cache — enforced by there being exactly one write path (`src/auth/token-storage.ts`, itself only ever called through an injected `SecureStoreAdapter`) and no other module in the app importing a competing storage mechanism for a credential. A Phase A repair pass replaced an earlier two-independent-keys scheme after independent review: storing access + refresh as two separate SecureStore writes left a window where a second-write failure could pair a new access token with an old, already-server-side-consumed (single-use) refresh token, colliding with the backend's replay-family revocation. A SecureStore write failure occurring *after* a successful server refresh now fails closed (best-effort clear, end the session, `TOKEN_STORAGE_ERROR`) rather than risking that old token ever being retried. Every unit test injects an in-memory fake adapter (`createInMemorySecureStoreAdapter`); none touches a real device keychain.
- **An authenticated bootstrap failure can never become an infinite loading screen.** A Phase A repair pass added a `bootstrap-error` route state: a consent/profile query that settles into a permanent failure (offline at launch, timeout, backend 5xx) previously left `resolveBootstrapRoute()` reading `undefined` data as `loading` forever. The fix checks each gating query's `isError` before the still-loading branch, and both `/` and the protected `(app)` layout render a deliberate reconnect surface with Retry — never signing the user out or touching stored credentials on a transient failure.
- **At most one `POST /refresh` call in flight at a time, no matter how many concurrent requests 401 simultaneously.** `src/auth/refresh-coordinator.ts` memoizes a single in-flight refresh promise; every other 401'd caller awaits that same promise and retries its own original request exactly once with the new access token. This is required, not merely efficient: the backend's refresh rotation is single-use with family-wide revocation on replay (`backend/app/main.py`'s `/refresh` docstring) — two concurrent refresh calls sharing one refresh token would collide with that exact defense and could revoke a legitimate session. Proven with 8 real concurrent 401'd calls in `tests/auth/refresh-coordinator.test.ts`, asserting exactly one refresh call.
- **A network/backend outage while refreshing can never be mistaken for an invalid session.** Only a definite 401/403 rejection of the refresh token itself clears SecureStore and ends the session; a network/timeout/5xx failure calling `/refresh` leaves the (possibly still-good) refresh token untouched and does not sign the user out. Proven directly (`tests/auth/refresh-coordinator.test.ts::"network/server failure during refresh itself does NOT end the session"`).
- **Bootstrap never makes a network call.** `src/auth/restore-session.ts::restoreSession()` decides `SIGNED_OUT`/`AUTHENTICATED` purely from whether a refresh token exists locally — so a dead network at launch can never look like "no credentials," and the app never hangs waiting for connectivity before rendering anything.
- **No local, client-cached consent boolean exists.** `GET /consent` (new, additive, read-only backend route — no existing behavior changed) is the only source of consent status; the navigation decision boundary re-routes into onboarding-consent the instant `has_valid_consent` is `false`, including a backend-side required-policy-version bump the client never has to know about in advance.
- **Every console log line is redacted through one function** (`src/utils/logger.ts`) before it reaches `console.*` — passwords, tokens, `Authorization` headers, and allergy/pregnancy/nursing fields are stripped recursively, proven with nested-object test cases.
- **The one navigation decision boundary is a pure, directly-unit-tested function** (`src/navigation/bootstrap-route.ts`), not logic scattered across screens — so "under what conditions does a signed-out user ever see the app shell" has exactly one place to audit, and that audit is itself part of the test suite (`tests/navigation/bootstrap-route.test.ts`), not just documentation.

### Phase B — camera capture and analysis (this pass)

- **Raw facial images are ephemeral on-device, exactly as they are server-side.** A captured photo lives only in the OS cache directory (`expo-camera`'s own default capture location; never the photo library, never `AsyncStorage`/SQLite/`SecureStore`/a persisted Query cache/a log line) for the duration of one capture-review-submit cycle. `src/analysis/capture-file.ts` is the one place base64 image data is ever produced, held only as a plain local variable for the duration of one `submitAnalysis()` call — proven never to reach a log line (`tests/analysis/capture-file.test.ts` asserts the produced base64 string appears in no logger call) and never placed in Query cache or global React state (structural: no code path does so).
- **Local temp-file cleanup distinguishes the prepared working copy from the original capture (post-merge audit repair pass — corrects an earlier version of this document's claim that a failed submission "deliberately leaves the temp files in place").** `deleteLocalCaptureFile()` never throws and never logs the file URI. The **prepared/resized working copy** (`prepareCaptureForSubmission()`'s own output) is deleted after every submission attempt, success or failure alike (`use-submit-analysis.ts`'s `try/finally`) — it must never accumulate across retries, since a fresh working copy is produced on each attempt. The **original capture** is retained only across a *transient submission failure* (a retry needs the identical photo, and the request-id policy below depends on that retry being a true retry of the same capture attempt, not a fresh one), and is deleted on confirmed submission success, on retake, on explicit Cancel, and on the capture screen's own unmount (`tests/analysis/capture-file.test.ts`, `tests/analysis/use-submit-analysis.test.ts`).
- **request_id identity is bound to the individual captured photo, not to the capture screen's lifetime (post-merge audit repair pass — corrects the original `AnalysisSessionProvider` design).** The original design held one `request_id` for the entire `(app)/analysis/*` route-session, which let a failed submission followed by Retake resubmit a *different* photo under the *same* `request_id` — the backend's own idempotent-replay behavior would then honor that literally, returning the first photo's analysis for the second photo's submission. `src/analysis/capture-attempt.ts`'s pure reducer now mints a fresh, cryptographically random `request_id` on every new capture and discards it entirely on Retake/Cancel, so a `request_id` and the exact photo it identifies are created and destroyed together (`tests/analysis/capture-attempt.test.ts`, including the specific "server accepted the first photo but the response was lost, then Retake, then a second photo" scenario).
- **A visible Cancel control exists in both the live-camera and review capture states (post-merge audit repair pass — this document previously described cleanup-on-cancel while no actual Cancel UI existed).** Cancel and Retake are both disabled while a submission is in flight (`submission.isPending`), so neither can race an active `POST /api/v2/analyses` and strand the user between accepted backend state and an abandoned local capture.
- **Only the camera permission is ever requested.** `app.json`'s `expo-camera` plugin config explicitly sets `recordAudioAndroid: false`, the `CameraView` itself is configured `mode="picture"` (this app never records video, so there is no code path that could prompt for microphone access), and no code path calls a microphone/contacts/location/Bluetooth permission API — verified by there being no such import anywhere in `mobile/src` or `mobile/app`.
- **A captured photo is never submitted to `takePictureAsync()` before the camera itself is ready, and never twice concurrently.** `src/analysis/camera-capture-policy.ts::canStartCapture()` gates the Capture button on both `cameraReady` (set by `CameraView`'s own `onCameraReady`) and the absence of an already-in-flight capture — a rapid repeated tap cannot produce two photos or orphan a temp file.
- **The mobile client's own image resize is not treated as a security boundary by the backend (post-merge audit repair pass).** `POST /api/v2/analyses` independently enforces its own encoded/decoded payload size limits and a cheap, header-only (Pillow, never a full pixel decompression) image-dimension/pixel-count check before the image is ever stored or handed to a worker — see `ASYNC_ANALYSIS_ARCHITECTURE.md`. A rejection at any of these stages releases the usage-quota reservation it consumed.
- **Consent can be revoked mid-flow without a client-side bypass.** A capture already reviewed and submitted still goes through the backend's own consent check on `POST /api/v2/analyses`; a live 403 routes the capture screen back to `(onboarding)/consent` rather than the app inferring or caching consent validity itself.
- **An ABSTAINED metric can never render a fabricated numeric value.** `src/analysis/analysis-presenter.ts::formatMetricValueForDisplay()` returns `null` for any `ABSTAINED` metric regardless of what its `value` field actually contains, and every render call site goes through this one function — proven directly, including the adversarial case of an ABSTAINED metric whose `value` is non-null (`tests/analysis/analysis-presenter.test.ts`).
- **A permanently-failed poll (404/403/other nonretryable status) never renders as an indefinitely "queued" analysis (post-merge audit repair pass).** `src/analysis/analysis-lifecycle.ts::isPermanentPollingError()` classifies purely off `ApiError.retryable`; a permanent failure stops polling immediately and renders a dedicated "This analysis isn't available" state with a "Start over" recovery path, distinct from both an in-progress analysis and an actual backend-reported `FAILED` one.
- **No clinical/diagnostic language.** Result copy uses "estimate"/"image-derived"/"could not measure reliably"; Capture Coach copy never states makeup must be removed (the backend cannot reliably detect it) and carries no medical claim.
- **Camera/privacy copy accurately describes on-device storage (post-merge audit repair pass — corrects prior "never saved to your device" wording).** The capture screen, `app.json`'s `cameraPermission` string, and this document all now say only what is true: a captured photo is temporarily stored in this app's OS cache for analysis, is never added to the photo library, and its working copies are deleted after submission, retake, or cancel *when those lifecycle paths actually run* — React's own unmount cleanup is not guaranteed after a force-kill or device crash, and no claim here says otherwise.

### Phase C1 — recommendation experience (this pass)

- **The safety-filtering-before-product-matching-before-client-presentation invariant now extends all the way to the client, not just to the database.** Mobile never re-runs `ProductMatchingService`, never calls `SafetyEngine`, and never substitutes a different formulation for one the backend already excluded — `[analysisId].tsx` renders exactly the rows `GET /api/v2/analyses/{id}`'s `product_recommendations` field returns, associated to routine steps only by the backend's own `plan_step_key` (`getRecommendationForRoutineStep()`, never array position). This phase adds no new safety logic that could weaken `test_unsafe_routine_status_never_coexists_with_concrete_recommendations` (`PRODUCT_RECOMMENDATION_PIPELINE.md`'s central invariant) — only a read/display layer on top of it.
- **An unrecognized `safety_status` value fails closed, never presented as a normal recommended product.** `getSafetyStatusPresentation()` (`src/analysis/product-recommendation-presenter.ts`) only renders calm neutral copy for `SAFE` and visible-restriction copy for `RESTRICTED`; anything else — which the backend invariant says should never happen, but this client does not assume that invariant holds forever — renders a generic "compatibility could not be confirmed" label and suppresses restriction/verification detail entirely (`isKnownSafetyStatus()`), and never crashes. Proven directly, including the adversarial case of a garbage status string (`tests/analysis/product-recommendation-presenter.test.ts`).
- **`product_recommendations` (`app/api/v2/analyses.py::ProductRecommendationOut`, `app/db/analysis_repository.py::get_product_recommendations()`) never exposes `id`/`user_id`/`analysis_request_id`/`created_at`**, same reasoning and same belt-and-suspenders pattern (SQL projection AND an independent Pydantic field allowlist) as `get_measurements()` already used for `analysis_measurements`. RLS already scopes the row to its owner regardless — this is a separate, deliberate minimization concern, proven directly (`tests/api/test_analyses_v2.py::test_get_completed_analysis_product_recommendations_projection`) and at the repository layer independent of the HTTP route's owner-vs-nonexistent-404 collapsing (`tests/analysis/test_analysis_repository.py::test_get_product_recommendations_denies_another_user`).
- **A completed analysis's displayed product name/brand/verification date can never silently drift after the fact.** Migration `366861ec262d` added nullable snapshot columns (`brand_name_snapshot`/`product_name_snapshot`/`verification_date_snapshot`) populated at commit time from `StepProductRecommendation`; `get_product_recommendations()` prefers that snapshot over a read-only current-catalog join, so a later brand/product rename in the catalog never changes what an already-completed analysis shows it recommended — proven directly by mutating the catalog row after commit and asserting the pre-mutation snapshot values still come back (`test_get_product_recommendations_persists_and_prefers_display_snapshot`). Older, pre-migration rows fall back to the current catalog rather than being backfilled with fabricated historical metadata; an unresolvable field is `null`, never invented (`test_get_product_recommendations_falls_back_to_current_catalog_when_snapshot_is_null`).
- **`rank_position` is never rendered as a clinical-efficacy or popularity claim.** It is compatibility-ordering provenance only (`ProductMatchingService`'s own "commercial firewall" docstring) — no copy anywhere in `ProductRecommendationCard`/`product-recommendation-presenter.ts` says "#1 product," "best product," or "top ranked product," asserted directly by test.
- **No raw machine reason code, and no invented medical interpretation, ever reaches the user.** `describeReasonCode()` maps the actual codes `SafetyEngine` emits to plain-language copy; an unmapped code degrades to the fixed fallback "Additional compatibility considerations apply." — never the raw code string, never a diagnosis. `summarizeRestrictions()` only recognizes the specific JSON shapes `evaluate_product_formulation()` actually produces and silently ignores anything else, rather than dumping raw restriction keys/values onto the screen.
- **No commerce/affiliate surface exists, deliberately.** No price, "Buy now," retailer/affiliate link, savings percentage, popularity score, or efficacy stars anywhere in `ProductRecommendationCard` — the catalog has no trustworthy generalized commerce data to render honestly, and this phase's own scope explicitly excludes inventing any.
- **A routine step with no concrete product match is never hidden and never backed by a client-chosen substitute.** `getRecommendationForRoutineStep()` returning `null` (no match, or an unexpected duplicate `plan_step_key` it deliberately refuses to guess between) renders a "No specific product match is available for this step yet." notice; the step's own action/category/why text renders unconditionally regardless.

## What's explicitly NOT done (see CV_VALIDATION_LIMITATIONS.md and OPEN_ENGINEERING_ITEMS.md for full detail)

- No catalog-administration route exists — catalog data is migration/fixture-only, not writable via any HTTP path.
- No cell-based routing, replication, or sharding exists — `home_region`/`cell_id` are metadata-readiness columns only (see `PRODUCTION_ARCHITECTURE.md` principle 7).
- No metrics/Prometheus backend is deployed — `app/observability/events.py`'s structured events are real, wired-in log lines, not yet fed into a time-series/alerting system.

- Cross-restart active-analysis restoration is deferred (`OPEN_ENGINEERING_ITEMS.md` item 6a) — an app restart mid-analysis returns the user to the app home rather than resuming the polling screen; the analysis itself is unaffected server-side.
