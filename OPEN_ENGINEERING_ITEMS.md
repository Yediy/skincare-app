## P0 — Release blockers

19. **CLOSED (`fix/revenuecat-entitlement-resource-id` hotfix).** `RevenueCatReconciliationService` compared RevenueCat API v2's `active_entitlements[].entitlement_id` — RevenueCat's INTERNAL entitlement resource ID (e.g. `entla1b2c3d4e5`) — directly against `settings.revenuecat_entitlement_id`, the human/business lookup key (e.g. `premium`) used by the webhook, the local projection, and mobile `requiredEntitlementIdentifier`. These are two distinct RevenueCat identifiers for the same entitlement resource and can never equal each other on a real RevenueCat response, so reconciliation (`POST /api/v2/billing/sync` and any future batch runner) could never actually detect an active entitlement through this endpoint — masked by `test_revenuecat_reconciliation_http_contract.py`'s own fixture fabricating `{"entitlement_id": "premium"}`. Fixed: a new required-when-billing-enabled setting, `REVENUECAT_ENTITLEMENT_RESOURCE_ID`, is matched against that one field (`_find_active_entitlement_by_resource_id`); the local `user_entitlements` projection, webhook gating, and mobile config are all unchanged and remain keyed by the lookup key. See `REVENUECAT_INTEGRATION_NOTES.md` section 5, `BILLING_ARCHITECTURE.md`'s "Reconciliation" section, and `SECURITY_AND_SAFETY_NOTES.md`.

2. **CLOSED (production-recommendation pass, then hardened further this continuation).** `PlanService.generate_plan()` still produces its abstract, category-level plan via `evaluate_offer()` (unchanged), but `apply_product_matching_and_routine_safety()` now runs on top of it in the real production path (both `/analyze` and the async worker, via the shared `compute_analysis()`), resolving categories to concrete catalog products through `ProductMatchingService` + `SafetyEngine.evaluate_product_formulation()` + `evaluate_routine_safety()`. Every concrete product recommendation now passes formulation-level safety, never just category-level. **This continuation's own P0 fix**: the routine-level conflict-resolution pass could previously exit with `routine_decision.status == UNSAFE` while still attaching concrete products regardless (an EXCLUDE-action frequency/barrier rule, or an unresolved `EXCLUDE_COMBINATION` its heuristic couldn't attribute) — fixed with an explicit attribution mechanism plus a hard backstop that clears every step's concrete candidates whenever the routine can't be made safe. See `SECURITY_AND_SAFETY_NOTES.md` and `PRODUCT_RECOMMENDATION_PIPELINE.md`.
