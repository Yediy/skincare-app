Classified into P0 (release blockers) / P1 (pre-launch) / P2 (post-launch) / P3 (research/moat). Nothing here is marked complete because scaffolding exists — every item below reflects real, verified absence or partiality, not assumption.

## P0 — Release blockers

2. **Allergy/avoid-ingredient enforcement is category-level, not per-product**, because no product/offer catalog exists in this repository at all. `app/domain/product_safety.py` is a deliberate, static, hand-authored adapter — real enforcement against real per-SKU ingredient data requires that catalog to exist first.

## P1 — Pre-launch

4. **No billing/subscription/webhook code exists.** RevenueCat lifecycle correctness, out-of-order webhook protection, and duplicate-webhook idempotency are all moot until a billing integration exists at all. An `EntitlementService`/`UsageService` interface seam (so business logic asks "does this user have entitlement X?" rather than depending on RevenueCat directly) is design-only — not built this pass, real effort not yet spent.
5. **No rate limiting or quota system exists.** `app/middleware/` is still empty. Needs an atomic Redis mechanism (Lua/Redis Function), not a non-atomic get-increment-check — not built this pass.
6. **No mobile app exists.** `mobile/` is empty directory scaffolding — raw-photo `AsyncStorage` persistence, client-side consent versioning, and all mobile-specific security items are unverifiable because there is no mobile codebase to check.
8. **The `@app.on_event("startup"/"shutdown")` pattern in `app/main.py` is deprecated** by FastAPI in favor of lifespan context managers — still functional (confirmed working throughout this entire pass, including the real Docker container built and run this pass), but flagged in every test run's warnings. Low urgency, but will eventually need migrating.
9. **Dependency version drift** between `requirements.txt` and what's actually installed/tested keeps recurring. This pass's own concrete instance: `boto3`/`botocore` were pinned in `requirements.txt` but not actually installed in the dev `.venv` until this pass needed them for `app/storage/r2.py` — caught immediately because the new tests failed to import, not silently. Recommend a CI step that fails if `pip install -r requirements.txt` can't resolve cleanly into a fresh venv (partially covered by `ci.yml`'s install step already; the new `dependency-scan` job added this pass, `pip-audit`, at least ensures the pinned set is scanned for known CVEs, though that's a different check than drift detection).
15. **No CV worker, queue consumer, or usage-reservation/quota ledger.** The domain boundary (`app/domain/analysis_service.py`), a generic `JobQueue` abstraction (`app/queue/`), and idempotent enqueue-by-`request_id` were built this pass (see "What was closed out" below) — but `/analyze` still runs `FacialAnalysisPipeline` synchronously inline on the API's event loop; nothing calls `enqueue`/`claim` from any real code path yet (`FAILURE_DOMAINS.md`'s CV-worker entry still flags the real risk this creates: a pathological image can hold one replica's event loop hostage for the duration, since mediapipe/opencv calls aren't `await`ed). Also still missing: an `analysis_usage` quota-reservation ledger (Phase 18) — a real, separate piece of work from job-level idempotency, needed before any billing/free-tier-limit feature can depend on it.
16. **No `home_region`/`cell_id` fields on `users`, and no routing abstraction.** Schema/contract compatibility with a future cell-based topology (`PRODUCTION_ARCHITECTURE.md`'s target architecture) is not yet in place — deferred, per this pass's own explicit instruction not to build cells before they're needed (`SCALING_TRIGGERS.md`).

## P2 — Post-launch

10. **No notification system exists** of any kind (no outbox, no dedup). Includes the broader transactional-outbox pattern for domain events (`USER_CREATED`, `ANALYSIS_COMPLETED`, etc.) described in this pass's brief — not built.
11. **`allergies`/`avoid_ingredients` are stored as plain text arrays**, not normalized ingredient entities. Documented explicitly as a placeholder in `app/db/profile_repository.py` and `app/domain/product_safety.py`; migrating to a real ingredient/allergen entity model — `products`/`ingredients`/`product_ingredients`/`ingredient_aliases` per this pass's brief — is a real, larger project once a product catalog exists to normalize against. Not built this pass; still blocked on P0-2 below.
12. **Ranking is still an interim additive model** (`_rank_priorities_by_severity`), not the `severity × confidence × persistence × intervention-value` multiplicative model this pass's brief describes as preferred. That model needs real per-metric confidence data (Phase 9/10) as an input before it can be built honestly — building it now would mean fabricating the confidence term. The "commercial firewall" ranking-stage ordering (safety before suitability before evidence before preference before budget before availability before commercial tie-break) this pass's brief also asks for has no product/commission data to rank in the first place yet, so it's design-only.
13. **No professional review mode, B2B analytics, or affiliate product ranking** — none of these have any code, and per the brief's own Section 22, none should be started before the P0/P1 items above are resolved.
17. **No metrics/observability pipeline or structured logging beyond Python's stdlib `logging`.** `sentry-sdk` is pinned in `requirements.txt` but not wired into `app/main.py` — no request rate/latency/error metrics, no analysis-duration or capture-quality-distribution metrics, no correlation IDs threaded through logs. `app/observability/` remains an empty package.

## P3 — Research / moat (explicitly not started, per the brief's own Section 22)

14. Personal Baseline Engine, Digital Twin, Outcome Engine, adaptive N-of-1 experiments, full ingredient knowledge graph, microservices/large module reorganization. None of these exist, and none should be started until the P0/P1 items above are resolved.
